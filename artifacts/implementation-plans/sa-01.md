# Plan for Implementing Story: sa-01

Story: `artifacts/stories/sa-01-client-registry-management-ui.md`

## Tasks
1. App: extend ClientRegistryService with CRUD methods
  - Description: Add to `App/Services/ClientRegistryService.cs`: `CreateClientAppAsync(string name, string redirectDomain, Guid createdBy) : Task<(ClientApp ClientApp, string PlaintextSecret)>` (generates secret via `Guid.NewGuid().ToString("N")`, hashes via `ClientSecretHasher`, saves); `GetClientAppsAsync() : Task<List<ClientApp>>` (includes `CreatedByUser` via `Include`); `UpdateClientAppAsync(Guid clientId, string name, string redirectDomain) : Task<bool>` (false if not found); `DeleteClientAppAsync(Guid clientId) : Task<bool>` (false if not found). Inject `ClientSecretHasher` into the service constructor.
  - Acceptance Criteria: Create persists a new `ClientApp` with a hashed secret and returns the plaintext once; List returns all client apps with creator username populated; Update changes Name/RedirectDomain for an existing client app and returns false for an unknown id; Delete removes the row and returns false for an unknown id. Covered by `App.Tests/ClientRegistryServiceTests.cs`.
  - Status: Completed

2. Api: ClientAppsController
  - Description: Add `Api/Controllers/ClientAppsController.cs` at route `api/client-apps`: `POST` `[Authorize(Roles = "Admin")]` (body: name, redirectDomain; returns 201 with clientId + plaintext secret); `GET` `[Authorize(Roles = "Admin,Operator")]` (returns list DTO: clientId, name, redirectDomain, createdOn, createdByUserName — never the secret/hash); `PUT {id}` `[Authorize(Roles = "Admin")]` (body: name, redirectDomain; 404 if unknown id); `DELETE {id}` `[Authorize(Roles = "Admin")]` (404 if unknown id). `CreatedBy` on create is read from the caller's `ClaimTypes.NameIdentifier` claim.
  - Acceptance Criteria: Admin can create/list/update/delete via the endpoints; Operator can list but gets 403 on create/update/delete; unauthenticated requests get 401/redirect per existing cookie-auth behavior. Covered by `Api.Tests`.
  - Status: Completed

3. Api.Tests: ClientAppsController tests + retarget RoleAuthorizationTests
  - Description: Add `Api.Tests/ClientAppsControllerTests.cs` covering create/list/update/delete happy paths and Operator-forbidden cases, seeding via `ApiWebApplicationFactory`. Update `Api.Tests/RoleAuthorizationTests.cs` to hit `GET /api/client-apps` (Admin+Operator allowed) and `POST /api/client-apps` (Admin-only) instead of the deleted `WeatherForecastController`.
  - Acceptance Criteria: All `Api.Tests` pass; `RoleAuthorizationTests` no longer references `WeatherForecastController`/`/WeatherForecast`.
  - Status: Completed

4. Client: ClientApps page authorization
  - Description: Add `Client/Pages/ClientApps.cshtml` + `ClientApps.cshtml.cs` (`PageModel` with `[Authorize(Roles = "Admin,Operator")]`).
  - Acceptance Criteria: Unauthenticated navigation redirects to `/Login`; authenticated `User`-role navigation redirects to `/AccessDenied`; Admin/Operator can load the page.
  - Status: Completed

5. Client: ClientApps page UI
  - Description: Build out `ClientApps.cshtml`: a list/table of client apps (name, redirect domain, creator, created date) populated via `fetch('/api/client-apps')` on load; a create form (name, redirect domain) visible only for Admin, posting to `POST /api/client-apps` and displaying the returned plaintext secret once in a dismissable alert; per-row edit (name, redirect domain) and delete controls visible only for Admin, calling `PUT`/`DELETE /api/client-apps/{id}`, with a confirm step before delete. Operators see the read-only list with no create/edit/delete controls. Follow the vanilla-JS `fetch()` + Bootstrap pattern from `Login.cshtml`; add a nav link in `Shared/_Layout.cshtml`.
  - Acceptance Criteria: Admin can register a client app and see the secret shown once (not retrievable afterward); Admin can view the list, edit a client app's name/redirect domain, and delete a client app; Operator sees the list but no create/edit/delete controls; server-side authorization is the actual enforcement (UI hiding is presentation-only).
  - Status: Completed

6. Postman collection
  - Description: Add a new Postman collection (e.g. `artifacts/postman/identity.postman_collection.json`) with requests for `POST/GET/PUT/DELETE api/client-apps` and `POST api/auth/login`/`logout` (needed to obtain the auth cookie before exercising client-registry requests).
  - Acceptance Criteria: Collection file is valid Postman JSON; importing it and running login followed by the client-registry requests against a locally running instance succeeds.
  - Status: Completed

7. Update story status
  - Description: Mark `sa-01-client-registry-management-ui.md` status as implemented once tasks 1-6 are verified.
  - Acceptance Criteria: Story file status field updated.
  - Status: Completed

## Excludes
- Client secret regeneration/recovery flow (deferred to a future story).
- Multiple redirect URIs per client app (schema stays single `RedirectDomain`).
- Soft-delete / audit trail for deleted client apps.
